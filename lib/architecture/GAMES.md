## 5. SHARED GAME ARCHITECTURE (UPGRADED)

### 5.1 Game session lifecycle

**States:** `invited` → `active` → `completed` / `abandoned`

**Transitions:**
- `invited` → `active` – receiving partner accepts invitation.
- `invited` → `abandoned` – no response in 48 hours OR partner explicitly declines.
- `active` → `completed` – all rounds finished.
- `active` → `abandoned` – 24 hours of inactivity in current round, or 24 hours after round completion with no navigation.

### 5.2 Idempotency and concurrency control

**Idempotency keys:**
- Session creation endpoint accepts an `idempotency_key` (UUID generated by client). If the same key is received within 5 minutes, return the existing session instead of creating a new one. Store key in a separate table `session_idempotency_keys` with TTL.

**Concurrency – simultaneous answers:**
- When both partners submit an answer for the same round at nearly the same time, use a database transaction with `SELECT FOR UPDATE` on the `game_session_rounds` row.
- Only the first transaction to set `both_answered = true` wins. The second transaction sees the updated row and does not trigger a duplicate reveal.

**Atomic counters:**
- `skips_used_a` and `skips_used_b` (Truth or Dare) are updated using atomic increment/decrement: `UPDATE game_sessions SET skips_used_a = skips_used_a + 1 WHERE ... AND skips_used_a < 1`. The update fails if already used, preventing double-skip.

### 5.3 Authentication and authorisation

- Every edge function (create session, submit answer, reveal, skip, etc.) verifies the user’s JWT token.
- After authentication, the function validates that the requesting user belongs to the relationship associated with the `session_id` (or `relationship_id` for creation). If not, return HTTP 403 with a generic error message.

### 5.4 Input validation and resource limits

**Per‑request validation:**
- `session_id` must be a valid UUID and belong to the user’s relationship.
- `answer_a` / `answer_b` must be either `'a'` or `'b'` (This or That) or a non‑empty string with max length (200 for Truth or Dare truths, 400 for 36 Questions). Reject invalid values with error code `INVALID_INPUT`.
- `chosen_type` (Truth or Dare) must be `'truth'` or `'dare'`.

**Rate limiting (per couple):**
- Game initiation: max 5 per hour.
- Answer submission: max 1 per 2 seconds per user.
- Remind button: max 1 per 4 hours per session (server‑side enforced via `remind_last_sent_at` column).

### 5.5 Timeouts and retry logic

**External service timeouts:**
- Claude API call (36 Questions observation): 10 seconds timeout. On timeout, skip the observation (no insight shown). Log timeout event.
- Push notification: 5 seconds timeout. On timeout, log failure but game continues; user will see in‑app notification banner instead.

**Client‑side retry for answer submission:**
- If answer submission fails due to network error, client retries with exponential backoff: 1s, 2s, 4s, max 3 retries.
- After all retries exhausted, show a persistent error banner: “Failed to save answer. Tap to retry.” User can manually retry.

### 5.6 Error handling and user messages

All API endpoints return errors in the following JSON format:

```json
{
  "error": true,
  "code": "RATE_LIMITED",
  "message": "Too many attempts. Please wait a moment."
}
```

**Error codes and messages (user‑facing):**

| Code | HTTP Status | User Message | Internal logging |
|------|-------------|--------------|------------------|
| `UNAUTHORIZED` | 401 | “Please sign in to play games.” | Log missing or invalid token |
| `FORBIDDEN` | 403 | “You don’t have access to this game.” | Log user_id, session_id mismatch |
| `NOT_FOUND` | 404 | “Game session not found.” | Log session_id |
| `RATE_LIMITED` | 429 | “Too many attempts. Please wait a moment.” | Log user_id, action, rate limit key |
| `ALREADY_ANSWERED` | 200 (idempotent) | No error – operation is ignored. | None |
| `SESSION_EXPIRED` | 410 | “This session expired. Start a new game.” | None |
| `CLAUDE_TIMEOUT` | 200 (graceful fallback) | No user message – observation simply omitted. | Log timeout |
| `INVALID_INPUT` | 400 | “Invalid value provided.” | Log invalid field |
| `INTERNAL_ERROR` | 500 | “Something went wrong. Please try again.” | Log full error with stack trace |

**Never expose internal error details to the client.**

### 5.7 Edge cases (complete table)

| Scenario | Expected Behavior |
|----------|-------------------|
| User’s phone dies mid‑answer | Answer saved locally. On app reopen, restore to question screen with saved answer. |
| Both partners submit answer simultaneously | Database transaction + row lock. First to commit sets `both_answered=true`. Second sees row updated and does not trigger duplicate reveal. |
| User submits answer for abandoned session | Reject with error code `SESSION_EXPIRED`. |
| User submits answer for already‑answered round | Idempotent: update same field again (no error, no duplicate reveal). |
| Partner unlinks relationship mid‑game | Session abandoned immediately. Both users notified. Game removed from both hubs. |
| User closes app after reveal but before “Next” | On reopen, resume at reveal screen for that round. |
| Claude API fails for 36 Questions observation | Skip observation. End screen shows only completion message. No user‑visible error. |
| Push notification service fails | Game continues. User sees in‑app notification banner instead. |
| User submits truth answer exceeding max chars | Trim to max length before saving. Show warning: “Answer trimmed to X characters.” |
| Custom question reported while session active | Question removed from current session. Next round falls back to preset. |
| User tries to start new game when one active | Show dialog: “You have an active game. Resume or abandon?” |
| User’s session is abandoned due to inactivity | Push notification sent: “Your game expired. Start a new one?” |
| Duplicate idempotency key for session creation | Return existing session (no new session created). |

### 5.8 Observability – logging, metrics, alerts

**Structured logging (all edge functions):**
- Log format: JSON with fields: `timestamp`, `level` (INFO/ERROR/WARN), `request_id`, `user_id` (hashed), `session_id`, `action`, `status`, `duration_ms`, `message`.
- Never log message content, answers, or raw PII.
- Log all API calls (session creation, answer submission, reveal, skip, etc.).

**Metrics (RED):**
- Rate: number of requests per endpoint per minute.
- Errors: error rate per endpoint (by error code).
- Duration: p50, p95, p99 latency for each endpoint.
- Business metrics: sessions started, completed, abandoned per game type and tone.

**Alerts (define in monitoring system):**
- Session creation failure rate > 5% in 5 minutes.
- Answer submission latency p95 > 1 second for 5 minutes.
- Claude API timeout rate > 10% in 10 minutes.
- Push notification failure rate > 10% in 5 minutes.

### 5.9 Pagination for past games

- Past games list uses **cursor‑based pagination** with a default page size of 20.
- Response includes `next_cursor` (timestamp of last item) for subsequent requests.
- Client can request more items with `?limit=20&cursor=<timestamp>`.

## 6. GAME 1 – THIS OR THAT (FULL INTEGRATED SPEC)

This section contains the complete This or That implementation, including custom questions, session history, and soft delete.

### 6.1 Game flow

- 10 rounds per session.
- Both partners answer the same binary question independently.
- After both answer, reveal shows both choices side by side with match indicator.
- Between rounds, the partner whose turn it is (alternating) chooses the next question source: Preset (random from Attune bank) or Custom (random from a partner’s shared custom questions).
- After 10 rounds, end screen shows match count, percentage, and most interesting pick.

### 6.2 Screen designs (key screens)

**Tone selector** (5 tones, default Connecting, Intimate requires consent gate)

**Invitation screen** – shows game, tone, duration; for Intimate, extra consent gate and fallback to Spicy if declined.

**Question screen** – two large tappable cards with emoji and text; partner answer status indicator; answers can be changed until both submit.

**Waiting screen** – shows your choice, waiting animation; remind button appears after 2 hours (rate‑limited to once per 4h, sends push to the partner who hasn’t answered).

**Reveal screen** – both answers side by side; match indicator text; slide‑in animation (300ms) and green flash on match; reveal sync uses `reveal_triggered_at` with 500ms grace window and polling fallback.

**End screen** – shows match count, progress bar (only if match percentage ≥60%; otherwise curiosity‑framed text), most interesting pick (first differing round → `is_interesting` flag → round 5). Buttons: Play again (returns to tone selector) and Try another game.

**Offline indicator** – banner when answer saved locally, retry every 30s.

**State restoration** – on app kill/reopen, restore active session, preserve unsynced answers.

**Session history** – list of all completed sessions in Games Hub; tap to view all 10 rounds with both answers; each user can hide a session from their own view (soft delete – partner unaffected).

### 6.3 Custom questions

Users can create their own This or That questions (max 100 chars question, 50 chars per option, optional emoji). Default sharing: shared with partner (can be made private). Custom questions are **not** tracked in `game_questions_seen` – they can repeat across sessions. Users can edit/delete their own questions, report inappropriate ones, and view usage count.

### 6.4 Selection algorithm (integrated)

Initial 10 questions per session are selected from three pools in priority:
1. **Custom questions** from either partner (shared, not private) – max 3 per session.
2. **Unseen preset questions** (from `game_questions_seen`).
3. **Seen preset questions** (allow repeats if necessary).

For Intimate tone: at least 5 of the 10 preset questions must be tone_level=4 (fill shortfall with Spicy).

For rounds 2‑10, the source is chosen by the partner whose turn it is – single question selected on demand from the chosen pool (preset or a specific partner’s custom questions). If no custom questions available, fallback to preset.

### 6.5 Database schema extensions (for This or That)

```sql
-- Additional columns for this_or_that
ALTER TABLE game_questions
ADD COLUMN option_a text,
ADD COLUMN option_b text,
ADD COLUMN emoji_a text,
ADD COLUMN emoji_b text,
ADD COLUMN is_interesting boolean DEFAULT false;

-- Custom questions table
CREATE TABLE custom_this_or_that_questions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid REFERENCES auth.users NOT NULL,
  question_text text NOT NULL CHECK (char_length(question_text) <= 100),
  option_a text NOT NULL CHECK (char_length(option_a) <= 50),
  option_b text NOT NULL CHECK (char_length(option_b) <= 50),
  emoji_a text,
  emoji_b text,
  tone text NOT NULL CHECK (tone IN ('connecting','romantic','playful','spicy','intimate')) DEFAULT 'connecting',
  is_private boolean DEFAULT false,
  times_used int DEFAULT 0,
  last_used_at timestamptz,
  report_count int DEFAULT 0,
  created_at timestamptz DEFAULT now()
);
-- RLS policies as defined in the spec

-- Additional columns on game_sessions
ALTER TABLE game_sessions
ADD COLUMN match_count int DEFAULT 0,
ADD COLUMN total_rounds_completed int DEFAULT 0,
ADD COLUMN remind_last_sent_at timestamptz,
ADD COLUMN hidden_by_user_ids uuid[] DEFAULT '{}';

-- Idempotency keys table
CREATE TABLE session_idempotency_keys (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  key text UNIQUE NOT NULL,
  session_id uuid REFERENCES game_sessions NOT NULL,
  created_at timestamptz DEFAULT now(),
  expires_at timestamptz DEFAULT (now() + interval '5 minutes')
);
```
