# Video Sharing (Gallery Pick, Trim, Send) — Design Spec

**Date:** 2026-08-15
**Status:** Approved by user, pending written-spec review
**Scope:** WhatsApp-style video sharing for Attune chat — pick a video from the gallery, trim it to fit a 3-minute cap, send. This is Part 1 of 2 planned video features. Part 2 (Snapchat-style ephemeral view-once camera capture) is an explicitly separate, later spec and entirely out of scope here.

## Goal

Let two people in a relationship send short videos to each other in chat, matching WhatsApp's actual video-attach behavior (pick → optional trim → send), to the same quality bar as the existing image and voice message features. Held to this repo's [Algorithm Quality Review Checklist](../../../lib/architecture/algorithms/algorithm_quality_review_checklist.md) (scope tags `[MOBILE][MUTATION]`).

## Why extend the existing media pipeline rather than build new infrastructure

Attune's chat media pipeline has already been widened once, from image-only to image+audio, for voice messages (`supabase/migrations/20260815120000_chat_voice_messages.sql`). That migration is the direct template here: the same `message-media` Storage bucket, the same `create_chat_media_upload_intent` RPC, the same `validate_message_media_before_insert` trigger, the same client-prepares/server-validates split already used for images and voice. Notably, `messages.media_type`'s own CHECK constraint already permits `'video'` — it was in the original schema and the voice migration's rewrite of that constraint preserved it (`CHECK (media_type IN ('image', 'video', 'audio'))`, confirmed directly against the current migration). What's missing is everywhere *else* that still hard-codes `('image', 'audio')`: the upload-intents table's own separate CHECK constraint, the RPC's internal type/MIME logic, and the trigger's type check. Video widens these allowlists again; it does not add a parallel stack.

## Why video compression is client-side only, with no server-side transcoding

This is the one architectural question with no direct precedent from images or voice — both of those are ready instantly on-device, and video's much heavier compression cost made "does the server need to help" a real question rather than an assumed default. Two infrastructure constraints rule out server-side transcoding for this app:

- **FFmpegKit (`ffmpeg_kit_flutter`), the standard Flutter video-transcoding package, is dead.** It was retired in January 2025 over Via-LA patent/licensing risk; its binaries were pulled from Maven Central, CocoaPods, and npm in April 2025, and the repository was archived in June 2025. Community forks exist but inherit the same unresolved patent exposure — not a safe foundation for a shipping app.
- **Supabase Edge Functions cannot transcode video.** They run in a Deno V8 isolate with no shell access and no ffmpeg binary; `ffmpeg.wasm` is tens of megabytes and exceeds the runtime's memory/CPU ceiling before finishing a real transcode. Supabase Storage's built-in image transform API (already used for image thumbnails) has no video equivalent. Server-side transcoding would require standing up a separate always-on worker (a container or VM) or paying for a third-party service (Mux, Cloudinary) — genuinely new infrastructure this app doesn't have, for a private two-person chat that doesn't need adaptive-bitrate streaming.

Client-side compression via a native-codec package (Android MediaCodec / iOS AVFoundation, not a bundled ffmpeg binary) keeps the server a pure validator — the same property that made the voice-messages pipeline easy to review — at the cost of variable compression time/quality across devices, which is bounded by the server's independent post-upload size re-check.

## Recording/Editing UX

Pick a video from the gallery (`ImagePickerService.pickVideo`, already implemented, never wired to chat) → a full-screen trim screen opens **unconditionally** for every gallery pick, pre-set to the full clip if it's already under the cap → confirm → compress → send. No cropping in this version (deferred to a future spec — chat video bubbles letterbox fine in their original aspect ratio, and building a crop pipeline for video would mean the same new rendering infrastructure the compression-architecture decision just ruled out).

- **Max duration: 3 minutes**, enforced primarily by the trim screen's draggable handles, which are physically clamped to a 3-minute-wide window and cannot produce a longer selection. A server-side byte-ceiling check (see below) is the authoritative backstop against a hostile or broken client, not a true duration probe — Storage object metadata exposes size and MIME for free but not video duration without decoding the container, so bytes are used as a calibrated proxy for the actual threat (someone uploading a huge file), exactly as this pipeline already does for image (800KB) and audio (1.2MB) ceilings.
- **Minimum duration: 500ms**, mirroring `VoiceRecorderService.minDuration` — below this, treated as accidental, not an error.
- **Target output: 800kbps video, 720p longest edge, H.264, AAC audio at 64kbps mono.** A 3-minute clip at this bitrate is ≈19.4MB, comfortably under a 25MB hard ceiling. This trades some quality on high-motion footage for staying under a sane upload size — appropriate for a mostly-static relationship-chat clip (talking, not action footage), and bitrate is the cheaper thing to trade against a duration cap that was an explicit, already-made product decision.
- **Pre-transcode source guard: 300MB, calculated against the *selected trim window's estimated bytes*, not the full source file's size.** A guard on full source size would reject exactly the case the trim screen exists to rescue — a large, long source video the user only wants a short clip from. The 300MB threshold is a transcode-feasibility gate (preventing a doomed multi-minute encode of an absurd input on a low-end device), not a quality gate; it sits far above any realistic trimmed phone-camera clip and should essentially never fire on legitimate input.
- **No hard outer bound on source video length before the trim screen.** Duration alone costs nothing before transcoding (a cheap metadata probe, no decode), and a very long source trimmed down to a valid window transcodes exactly as fast as a short source of the same trimmed length. The trim screen's filmstrip scrubber handles arbitrarily long sources with a fixed-width strip and a draggable 3-minute-max window.
- **Over-ceiling compressed output (rare, high-motion footage): hard reject, no automatic retry at a lower bitrate.** Matches `ChatImagePreparer`'s bounded-attempt philosophy — video transcoding is slow enough that a silent retry ladder means a multi-minute wait before the user even learns it failed; better to fail once, clearly, and let them trim shorter or pick a different clip.
- **Thumbnail (poster frame) is generated client-side**, at the trim screen's selected start point, in the same preparation pass as compression — not via the existing async server-side processing outbox that generates image thumbnails today. This mirrors the reasoning that led voice messages to sample their waveform client-side rather than server-side: the poster frame is ready the instant the message is composed, with no "processing" wait before the bubble shows something real, keeping video consistent with voice's instant-readiness property rather than introducing a new intermediate state no other media type in this app has ever needed.

## Data Model

**`Message` entity** (`lib/features/chat/domain/entities/message.dart`) reuses every existing field from the voice-messages build with their meaning extended to video (`mediaKey` = the `.mp4`'s storage key, `mediaType` = `'video'`, `mediaThumbnailKey` = the poster's storage key, `mediaDurationMs` = trimmed duration, `localMediaPath` = local file path for optimistic playback, `waveform` stays null). One genuinely new field:

- `String? signedThumbnailUrl` — video-only, client-only (not persisted via `toJson`/`fromJson`, matching how `signedMediaUrl` is already excluded — signed URLs expire, and persisting one to the offline cache would rehydrate a dead link). Needed because, unlike image (where one URL suffices — the bubble only ever shows the thumbnail, and the fullscreen viewer, not built in this version, would re-sign on demand), video's bubble needs **both** URLs simultaneously: the poster to paint immediately and the mp4 to hand the player on tap. Squeezing both through one field would force a second round-trip on every tap.
- `bool get hasVideo => mediaType == 'video' && (signedMediaUrl != null || localMediaPath != null)` — mirrors `hasImage`/`hasAudio` exactly.

**Migration** (`supabase/migrations/20260815130000_chat_video_messages.sql`), widening the same sites the voice migration widened, in the same order, following the now-established pattern of enumerating every hard-coded site explicitly rather than trusting a partial list:

1. `messages.media_type`'s CHECK constraint already includes `'video'` — **no change needed**. (Verified directly against the current migration state before relying on this, not assumed.)
2. `message_media_upload_intents.media_type`'s own separate CHECK constraint — drop and recreate as `('image', 'audio', 'video')`.
3. `feature_flags` row: `INSERT ... ('chat_video_sharing', false) ON CONFLICT DO NOTHING`.
4. `create_chat_media_upload_intent` — `CREATE OR REPLACE` on the existing 3-argument signature (no arity change, no DROP-before-CREATE reordering concern this time, since voice already established `(uuid, text, text)`). Changes: accept `'video'` in the media-type check; MIME allowlist gains `video/mp4` only (not `video/quicktime` — the client always transcodes to mp4, so accepting a raw `.mov` upload would let a hostile client skip compression entirely); extension map gains the mp4 case; **the flag-enforcement branch, when `p_media_type = 'video'`, requires BOTH `chat_video_sharing` AND `chat_image_sharing` to be enabled**, since every video send also requires a thumbnail intent through the image path — this turns a confusing partial failure (video uploads, thumbnail intent creation 403s) into a single clear upfront rejection.
5. `validate_message_media_before_insert` — accept `'video'` in the type check; add a type-aware size ceiling (25MB for video, alongside the existing 800KB/1.2MB for image/audio). **New validation not present in the voice migration**: when `NEW.media_type = 'video' AND NEW.media_thumbnail_url IS NOT NULL`, validate the thumbnail against its own consumed intent (object existence, size, MIME) the same way the main media object is validated. This is a genuinely new check, not just a widened allowlist — previously `media_thumbnail_url` was always written by a server-side worker and never needed validation; video is the first media type where a client writes this field directly, and an unvalidated client-supplied value would let a client point the thumbnail at an arbitrary object in the bucket.
6. `enqueue_chat_media_processing`'s trigger `WHEN` clause already reads `NEW.media_type = 'image'` — video inserts skip it automatically, same as audio. No change needed; called out explicitly in the migration's comments so this isn't mistaken for an oversight.

**Two upload intents per video message** — the one structural departure from every other media type built so far, all of which are one-object-per-message. A video send requires both the `.mp4` and its poster frame as separate Storage objects, each consumed from its own intent (the trigger's intent-consumption model is one-intent-per-object, keyed by `media_url`). The thumbnail intent goes through the ordinary **image** path with no special-casing — it genuinely is a JPEG, sized well under the existing 800KB image ceiling (a poster frame is typically ~40KB), gated by `chat_image_sharing`.

**Storage RLS**: the existing `message_media_select_relationship_members` policy already matches on `m.media_url = name OR m.media_thumbnail_url = name`, so the client-written poster is readable by both partners with zero policy changes.

**Soft delete**: the existing tombstone logic already NULLs `media_url`, `media_type`, and `media_thumbnail_url` — video is covered as-is.

**Repository hydration** (`supabase_chat_repository.dart`): the `_hydrateMessages` gate that currently resolves a signed URL only for `mediaType == 'image' || mediaType == 'audio'` widens to include `'video'`, but with a type-aware fork rather than a single-URL resolution — video resolves **two** signed URLs in parallel (main object + thumbnail, both hitting the existing signed-URL cache), populating `signedMediaUrl` and the new `signedThumbnailUrl` respectively. A video row whose thumbnail failed to upload (see Error Handling) hydrates with `signedThumbnailUrl == null`, and the bubble falls back to a neutral placeholder.

## Client Architecture

**New dependencies**: `video_player` (playback, official Flutter package), `video_thumbnail` (native frame extraction via AVAssetImageGenerator/MediaMetadataRetriever), `video_compress` (trim + transcode to the target bitrate/resolution, also exposes duration/size probing and a compression-progress stream). `image_picker` is already present and its `ImagePickerService.pickVideo` method (already implemented, never wired to chat) needs no changes. The extracted thumbnail frame is compressed via the **existing** `ChatImagePreparer`, not a parallel image-compression path — it genuinely is just an image once extracted, and reusing that preparer means the thumbnail inherits EXIF-stripping, the 1600px longest-edge cap, and the 800KB ceiling for free.

**`ChatVideoPreparer`** (`lib/features/chat/domain/services/chat_video_preparer.dart`) — mirrors `ChatImagePreparer`'s shape exactly: a dependency-free service, static limit constants, one `prepare()` entry point, a typed `ChatVideoRejected(code)` exception carrying a coarse, content-free, loggable reason (matching `ChatImageRejected`/`VoiceRecordingException`'s pattern).

- Constants: `maxBytes = 25MB` (post-transcode output ceiling), `maxSourceBytes = 300MB` (pre-transcode guard, checked against the trim window's estimated bytes), `maxDuration = Duration(minutes: 3)`, `minDuration = Duration(milliseconds: 500)`, `targetHeight = 720`, target bitrate 800kbps video / 64kbps AAC mono audio.
- `prepare({required String localPath, Duration? trimStart, Duration? trimEnd, void Function(double)? onProgress})` — the `onProgress` parameter is a deliberate divergence from `ChatImagePreparer`'s signature: a multi-minute transcode with no progress feedback reads as a hung app, so it's wired to `video_compress`'s own compression-progress stream and surfaced through a modal progress UI at the call site.
- Flow, cheapest rejection first: existence/emptiness check → source-size guard (window estimate) → MIME sniff from the container's `ftyp` box magic bytes (never the file extension — the video analogue of `ChatImagePreparer`'s byte-sniffing, since a `.mov` renamed to `.mp4` must not be trusted) → probe (`getMediaInfo`) for duration/width/height, unreadable file rejected here rather than via a full decode → duration-bounds check against the effective (trimmed) duration → transcode at the target bitrate/resolution (single attempt, no quality-stepping ladder — video transcodes cost real time, and a retry ladder means a user waiting minutes to be told no) → post-transcode size check (hard reject over 25MB) → thumbnail frame extraction at the trim start point, routed through `ChatImagePreparer` for final compression, with a `ChatImageRejected` from that step caught and rethrown as `ChatVideoRejected('thumbnail_failed')` so callers only ever handle one exception type → return `PreparedChatVideo { file, mimeType, byteSize, durationMs, thumbnailFile, thumbnailMimeType, thumbnailByteSize, width, height }`.
- Both output files land in `getTemporaryDirectory()` via the same `_tempTargetPath` naming pattern `ChatImagePreparer` already uses, so the existing `_deleteStagedMedia` cleanup mechanism applies to video with no changes to that mechanism itself — only to the call sites that need to invoke it for a second (thumbnail) path.

**Trim screen** (`lib/features/chat/presentation/screens/video_trim_screen.dart`) — a full-screen route pushed via `Navigator.push`/`MaterialPageRoute` (not a GoRouter route, so it never appears in deep links and can't be reached without a source file already in hand — mirroring how other modal chat media UI is already pushed), opened after the picker returns and **before** `ChatVideoPreparer.prepare()` runs, so the single transcode encodes exactly the range the user selected.

- Takes the source path and probed duration; returns `({Duration start, Duration end})?` (null = user backed out, no send).
- A `VideoPlayerController`-backed preview at the top with tap-to-play/pause and seek-on-handle-drag.
- A filmstrip of evenly-spaced frames (extracted via `video_thumbnail`, cached in memory once on init) as the scrub track, with two draggable handles.
- Selection is **physically clamped** to `[minDuration, maxDuration]` by the handle logic itself — the UI cannot produce an out-of-range selection, which is why `ChatVideoPreparer`'s own duration-bounds check is a defense-in-depth backstop, not the primary enforcement mechanism.
- Live duration readout (e.g. "0:12 / 3:00"); the confirm button is disabled below the minimum duration.
- Appears unconditionally for every gallery pick, pre-positioned to the full clip's length when the source is already under the cap.
- M3 design-token compliance, 48dp minimum touch targets on the drag handles, filmstrip scrolls inside its own bounded box (no page overflow).

**`VideoMessagePlayer`** (`lib/features/chat/presentation/widgets/video_message_player.dart`) — built to match `VoiceMessagePlayer`'s established house style (hand-rolled, no third-party control chrome) rather than introduce a second playback UI convention, with one deliberate divergence:

- **Poster-first, lazy controller construction.** The bubble renders the thumbnail with a centered play button; a `VideoPlayerController` is not constructed until the first tap. This is the key difference from `VoiceMessagePlayer`, which eagerly constructs its `AudioPlayer` in `initState` — audio players are cheap to hold open across a whole message list, video decoders are not, and a list of ten video messages must not spin up ten native video surfaces.
- **One-at-a-time playback**, reusing the exact provider pattern voice messages established: a new `currentlyPlayingVideoMessageIdProvider` (in the same file as the existing voice provider), with the same `ref.listen` → pause-self wiring, additionally cross-pausing any currently-playing *voice* message on video start (and vice versa) — two simultaneous audio streams is the actual user-facing failure mode the one-at-a-time pattern exists to prevent, and it applies across media types, not just within one.
- **`dispose()` disposes the controller**, matching `VoiceMessagePlayer`'s no-background-playback guarantee — leaving the message list stops playback.
- **Local-vs-remote source branching** copies `VoiceMessagePlayer`'s `startsWith('http')` check: `VideoPlayerController.file` for a just-sent local clip whose upload hasn't landed yet, `VideoPlayerController.networkUrl` for a signed URL.
- **Identity keyed on `message.clientMessageId`, not `message.id`** — the same stability requirement the final voice-messages review caught and fixed for `VoiceMessagePlayer` (the optimistic message's id changes when the canonical server row replaces it mid-playback). This spec adopts that fix from the start rather than re-discovering it.
- Aspect ratio derived from the persisted `width`/`height` so the bubble reserves correct space before the poster image decodes (no layout jump). Bubble sizing matches the existing image branch's 220px max width, height derived from aspect ratio and capped so a vertical 9:16 clip doesn't dominate the viewport. Overlaid duration chip, mute toggle (starting unmuted — these are one-to-one intentional sends, not a social feed). No fullscreen viewer in this version (explicit out-of-scope).

**Attach bottom sheet** (modification to `chat_screen.dart` and `ChatTextField`) — the existing single-purpose photo icon becomes a general attach entry point. `ChatTextField`'s existing `showAttachImage`/`onAttachImage` parameters are **left unchanged** (any other caller of `ChatTextField` outside chat that passes only these two keeps its current single-tap photo behavior with no visible change). Two new, purely additive parameters are added alongside them: `showAttachVideo`/`onAttachVideo`. Only `chat_screen.dart`'s own composer passes both pairs; when both are present, tapping the (now-shared) attach icon opens a bottom sheet with Photo Library / Video Library rows (camera-capture rows are out of scope for this gallery-pick-only spec) instead of calling `onAttachImage` directly — each row filtered by its own feature flag (`chatImageSharingEnabledProvider` / a new `chatVideoSharingEnabledProvider`), shown whenever either flag is on. The sheet opens consistently even when only one flag is enabled, rather than special-casing a single-option flow into a direct picker launch — a button that sometimes opens a sheet and sometimes doesn't is the kind of inconsistency that reads as a bug.

`_attachVideo()` sits beside the existing `_attachImage()` with the same structure: pick → trim screen → `ChatVideoPreparer.prepare()` (behind a modal progress dialog fed by `onProgress`, cancellable via the underlying package's cancel API) → on `ChatVideoRejected`, a snackbar via a `_videoRejectionMessage(code)` switch mirroring the existing `_imageRejectionMessage` → on success, clear composer/draft/reply-target (same reasoning as the existing image path's comment: video replies are equally out of scope) → `sendVideoMessage`.

**`ChatController.sendVideoMessage`** mirrors `sendImageMessage`/`sendVoiceMessage`'s exact shape (`canSend` check, current-user null check, file-existence check, a belt-and-suspenders duration check against `ChatVideoPreparer.maxDuration` matching the existing comment pattern about a caller bypassing the preparer service, thumbnail-file-exists check, `PendingSend` construction → outbox write → optimistic `Message` → `_attemptSend`).

**`PendingSend`** (verified against its current actual shape before finalizing this spec) gains four new nullable fields — `localThumbnailPath`, `mediaWidth`, `mediaHeight`, `thumbnailMimeType` — added to both the constructor's named-parameter list and the unconditional field-pass-through inside `copyWith`'s body (confirmed: `copyWith`'s own parameter list only exposes `attempts`/`nextAttemptAt`/`lastErrorCategory`/`state`; every other field, including these new ones, must be threaded through its constructor call by reading the instance field directly, or it is silently dropped on every state transition — this is the existing pattern every prior field addition has had to follow correctly, not a new bug being introduced).

**`_attemptSend`'s media branch** gains the second intent/upload for video: request the video intent and upload the `.mp4` first, then (video only) request a second intent (`mediaType: 'image'`, since the thumbnail intent goes through the ordinary image path) and upload the thumbnail JPEG, then call `sendTextMessage` (now also accepting `mediaThumbnailKey`, `mediaWidth`, `mediaHeight` parameters) to insert the message row. Both objects are in Storage before any message row exists — a failure at either upload step throws into the existing `catch → _handleSendFailure` path unchanged, and a retry re-requests fresh intents rather than reusing expired ones.

**`_reconcileLocalMediaPaths`** (which preserves `localMediaPath` across the optimistic→canonical swap so a just-sent image keeps rendering from disk while its signed URL resolves) needs the identical treatment for `localThumbnailPath`, or a just-sent video's poster goes blank the instant the server row arrives — flagged explicitly here because this is exactly the class of gap ("a shared code path needs the same fix applied a second time for the new field") that has bitten this pipeline's build twice already, once for the signed-URL hydration gate and once for the intents CHECK constraint.

**`_deleteStagedMedia`** needs a companion call for `localThumbnailPath` at every existing call site that already cleans up `localMediaPath` (successful send, the duplicate-insert reconciliation path, manual failed-message removal, outbox eviction) — missing any one leaks a JPEG into the temp directory per affected send.

**`MessageBubble`/`_BubbleBody`** gains a `message.hasVideo` conditional branch alongside the existing `hasImage`/`hasAudio` branches, rendering a `VideoMessagePlayer` keyed `ValueKey(message.clientMessageId)` for the same stability reason already established for the voice player.

## Error Handling & Checklist Mapping

| Failure | Behavior |
|---|---|
| Picked file missing/empty | `ChatVideoRejected('media_missing'/'media_empty')` → plain-language snackbar, never a raw path or exception string. |
| Trim-window-estimated source too large (>300MB) | `media_too_large` — rare, since this is calibrated far above any realistic trimmed clip. |
| Unrecognized container format (not mp4/mov via magic-byte sniff) | `media_type_unsupported`. |
| Corrupt/undecodable file | `media_decode_failed`. |
| Selected duration under 500ms | Silent no-op, not an error — matches voice messages' identical below-minimum behavior. |
| Selected duration over 3 minutes | `media_too_long` — a backstop; the trim handles are physically clamped so this should be unreachable in normal use. |
| Compressed output still over 25MB | `media_compress_failed`, hard reject, no automatic retry at lower quality — video transcoding is too slow for a silent retry ladder to be a good user experience. |
| Thumbnail extraction/compression fails | `ChatVideoRejected('thumbnail_failed')` — blocks the send before it's queued (the file-existence check in `sendVideoMessage` catches this), since a message with no way to ever get a poster is a worse outcome than asking the user to retry. |
| Thumbnail **upload** fails after the video uploaded successfully | Non-fatal — the send proceeds with `media_thumbnail_url = null`. Losing an already-uploaded 25MB video over a missing 40KB poster is the wrong trade; the bubble falls back to a neutral play-button placeholder. |
| Video upload fails | Fails the send normally through the existing outbox retry path — no special-casing versus image/audio. |
| Compromised/stale client bypasses UI flags or MIME/size checks | Server-side: `create_chat_media_upload_intent` independently enforces both `chat_video_sharing` and `chat_image_sharing` flags for any video intent, the MIME allowlist, and relationship membership; `validate_message_media_before_insert` independently re-validates the uploaded object's real size/MIME against Storage metadata for both the video and (new) the thumbnail, each against its own consumed intent. |

**Checklist scope: `[MOBILE][MUTATION]`** (no `[ASYNC]` — unlike the image pipeline's thumbnail generation, video has no server-side background processing step; the client-side thumbnail is authoritative and synchronous with the send).

- **P0-U**: input validation both client-side (the full guard stack above) and server-side (never client-trust-only) — mirrors the bar voice messages was held to.
- **P1**: resource cleanup — every temp file (compressed video, extracted+compressed thumbnail) has a defined deletion path via the existing `_deleteStagedMedia` mechanism, extended to the thumbnail path at every call site. Cleanup on cancellation — a cancelled in-progress transcode (via the modal progress dialog's cancel action) must not leave a partial output file or a half-populated `PendingSend`.
- **P2**: graceful degradation is the table above, not "won't happen." Configurable thresholds — duration cap, bitrate, resolution, byte ceilings are named constants, not scattered magic numbers.

## Explicitly Out of Scope (this spec)

- Cropping (deferred to a future spec — trim-only in this version).
- A fullscreen video viewer (inline bubble playback only).
- Snapchat-style ephemeral view-once camera capture — separate, later spec (Part 2).
- Server-side transcoding, adaptive bitrate, or HLS streaming.
- Recording video from the in-app camera (gallery pick only — camera-record video is a natural fit for the future ephemeral-capture spec instead, not this one).
- Video replies (quoted video messages) — mirrors the existing image-message precedent of clearing any pending reply target on send rather than attaching it.

## Testing Evidence Plan

- Unit tests for `ChatVideoPreparer`'s pure-logic surfaces: MIME sniffing against known-good/known-bad magic byte sequences, duration-bounds branching (silent no-op below minimum, rejection above maximum), the source-size-guard's window-estimate formula, and confirmation the guard ordering is genuinely cheapest-first. Native calls degrade to typed exceptions in a pure-Dart test host, matching `VoiceRecorderService`'s established pattern, rather than throwing `MissingPluginException`.
- Widget tests for the trim screen: handle-drag clamping to `[minDuration, maxDuration]`, confirm button disabled below the minimum, correct pre-positioning for both already-short and over-cap sources.
- Widget tests for `VideoMessagePlayer`: poster-first rendering with no controller constructed before first tap, one-at-a-time enforcement across two video bubbles AND cross-media against a voice message, local-vs-remote source branching, and an explicit regression test that `clientMessageId`-based identity survives the optimistic-to-canonical message swap (the exact bug class the voice-messages final review caught for `VoiceMessagePlayer` — built in from the start here rather than re-discovered).
- Repository/outbox tests: `PendingSend` round-trip for the four new fields, `_attemptSend`'s two-intent sequencing (thumbnail intent requested and uploaded before the message insert; both the video-upload-fails and thumbnail-upload-fails cases exercised against their differing fatal/non-fatal behavior), `_reconcileLocalMediaPaths` preserving the thumbnail path across the optimistic swap, and every `_deleteStagedMedia` call site verified to also clean up the thumbnail path.
- Migration verification (manual, given this repo's standing gap of no live-Postgres access in an agent sandbox — the same limitation the voice migration hit): confirm the widened intents CHECK constraint, the RPC's paired-flag enforcement for video, the trigger's new thumbnail-intent validation, and an explicit assertion that `enqueue_chat_media_processing` still correctly skips video inserts.
